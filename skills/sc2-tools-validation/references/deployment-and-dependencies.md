# 部署与依赖完整性

## `deploy-mod.py`（以及 `deploy-mod.ps1`）

- 从 `agent-config.json` 读取 `project.source_mode`。
- `in_place` 模式下，`paths.mods_dir` 下配置的 Mod 本身就是权威源，所以部署是显式的空操作；直接编辑并校验那个源。
- `workspace_copy` 模式下 `project.source_mod`（工作区相对或绝对）是权威；路径缺失或非法会中止写入。配置的源向外部署到 `paths.mods_dir`。绝不把已部署目标上的改动倒着抄回来当作常规流程。
- 把 `.SC2Mod` 组件文件夹复制到 `agent-config.json` 里的 `paths.mods_dir`（可用 `--mods-dir` 覆盖）；它绝不重写生成的 `Lib*.galaxy`。
- 部署前先用 `--dry-run`；源与目标已经相同会被当作安全的空操作。
- 不带 `--dry-run` 时它 **不是** 只读校验命令，也不会重新生成编译库。

`workspace_copy` 部署之后，在 SC2 编辑器里打开并保存模组以重新生成编译库。`in_place` 模式下跳过部署，直接打开权威源。

部署对相同路径保持空操作，并在 dry-run、清理或复制之前拒绝祖先/后代重叠。

## 依赖完整性

所有调查工具共用同一个依赖根解析器。配置的编辑源保留配置的 Mods；一次性显式组件用它自己的 Mods 祖先。两者都不适用时，给检查/构建或测试套件传 `--mods-dir`。绝不要静默使用另一套安装里的同名模组。

组件依赖缺失或损坏时，当前 catalog 构建与查询会中止。`--allow-incomplete-dependencies` 允许带显式标记的部分只读调查；v3 清单会存下问题，每次查询都重复该警告。它不授权有效值确认、源写入或依赖校验。`--allow-stale` 是独立的历史许可。重建陈旧/缺失的清单，并带上真正的组件清单 info 文件。

关掉 `project.resolve_dependencies_recursive` 只会保留主组件结果，属于部分作用域；此时构建与查询都要求 `--allow-incomplete-dependencies`，并伴随「配置已禁用」的显式警告。

索引产物与清单绑定同一个 `build_id`；身份不一致一律中止。每条索引路径都会检查它记录的选择。历史遗留需要显式许可，且绝不覆盖部分依赖许可。构建先暂存完整输出再发布；仅 SQLite 模式会保留先前的 JSON/报告与手工附加物。

部署要么暂存干净的替换，要么合并复制，检查源稳定性与复制字节数，并保留一个自己拥有的上一版本。发布回滚失败会保留所有尚存的诊断路径；不要自动删除它们，也不要把新版本当成已接受。
