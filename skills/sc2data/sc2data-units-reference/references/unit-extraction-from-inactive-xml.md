# 从非活动 XML 中提取单位

参考流程：从 `XMLFromDependenciesWeDontUse/` 中重建选定单位，而不把其来源依赖加为活动依赖。

目标不是克隆一个非活动依赖，而是为项目战役单位提取最小且可靠的数据链：游戏性、必需的视觉/音频、指令面板集成与本地化。

以活动依赖导出与项目自身的模组目录作为编写参考。不要假设本地存在一个单独的参考模组。

## 来源目录

| 目录 | 在提取中的角色 |
|---|---|
| `Units.txt` | 从这里开始。定义属性、标志、技能链接、武器链接、行为链接、指令面板按钮、花费、载货、占地/Mover、死亡设置，以及创建/死亡效果挂点。 |
| `Abilities.txt` | 训练/建造/变形/研究/施放数据、指令按钮图标、花费、冷却、充能、自动施放校验器、技能效果，以及产出单位。 |
| `Weapons.txt` | 攻击周期/距离/过滤，以及第一个攻击效果链接。 |
| `Effects.txt` | 游戏性执行链：伤害、发射弹体、搜索、集合、持续、切换、施加/移除行为、创建单位、修改单位、传送与下达命令效果。 |
| `Behaviors.txt` | 被动状态、增益、光环、老兵等级、隐形、限时生命、受击响应、武器切换与变形辅助。 |
| `Actors.txt` | 视觉/音频事件层。单位 Actor 绑定 `unitName`；动作 Actor 绑定效果；模型/声音 Actor 创建次级特效/音频。 |
| `Models.txt` | Actor 使用的模型数据 ID：单位模型、头像、死亡模型、弹体、溅射、釉层、放置模型、命中/发射特效，以及按动画时点触发的声音负载。 |
| `Sounds.txt` | Actor 与模型事件使用的声音数据 ID：战斗音效、单位语音、界面音效、循环音效、过场/指挥官语音、音量/音高/衰减、字幕与头像元数据。 |
| `Buttons.txt` | 按钮图标、图标资源、热键、提示，以及被动的指令面板条目。 |
| `Requirements.txt` / `Requirement Nodes.txt` | 显示/使用门控。这些往往是最嘈杂的合作专属部分，通常应为项目重写。 |
| `Validators.txt` | 目标选取、自动施放、行为、玩家与 Actor 守卫。保留行为关键的校验器；简化指挥官/威望类校验器。 |
| `Movers.txt` / `Turrets.txt` | 仅当弹体、单位或武器引用了自定义移动或炮塔转向时才需要。 |
| `Upgrades.txt` | 字段变异模式。只复制代表实际战役单位机制的升级；跳过指挥官成长升级。 |

## 依赖图

按此顺序追踪候选单位：

1. `CUnit id="..."`。
2. 该单位上的每个 `AbilArray`、`WeaponArray`、`BehaviorArray`、`EffectArray`、`CardLayouts`、`TechAlias`、载货、占地、Mover 与炮塔引用。
3. 该单位链接的每个 `CAbil*`，包括 `InfoArray Unit`、`Effect`、`CmdButtonArray`、`AutoCastValidatorArray`、`Requirement`、`Cost`，以及冷却/充能链接。
4. 该单位链接的每个 `CWeapon*`，然后是它的 `Effect` / `DisplayEffect`。
5. 从技能与武器可达的每个 `CEffect*`，直到所有效果链终止。
6. 从单位、技能与效果可达的每个 `CBehavior*`。
7. 从技能、效果、行为、武器与 Actor 可达的每个 `CValidator*`。
8. 从技能、指令卡、训练条目与按钮可达的每个 `CRequirement*` 与需求节点。
9. `unitName` 与该单位 ID 匹配的主 `CActorUnit`，以及它所依赖的任何父级/复制来源假设。
10. 该 Actor 的事件与死亡/自定义字段引用的每个 Actor，尤其是 `CActorAction`、`CActorModel`、`CActorSound`、`CActorRange`、`CActorSplat` 与 `CActorBeam`。
11. Actor 或模型动画事件引用的每个 `CModel*` 与 `CSound`。
12. 显示名、提示、按钮、警报与编辑器对象名所需的每个 `CButton` 与本地化键。

复制之前，始终把候选 ID 与 `DataEditorXML/` 对照。有些非活动记录只是在活动战役记录之上的覆写。

若精简后的提取遗漏了模型、声音、炮塔、辅助武器、校验器与编辑器本地化，即便包含单位、效果、行为与 Actor，仍可能不完整。参见 [xml-patterns.md](../../../sc2-catalog-xml/references/xml-patterns.md#editor-round-trip-checklist) 中的编辑器往返检查清单。

## 完整单位与覆写补丁

非活动依赖导出有两种形态：

- 完整或接近完整的单位：非活动目录定义了单位、武器、Actor、模型、声音与大部分支撑性游戏性数据。
- 覆写补丁：非活动导出只是给已存在的战役单位加上依赖专属的行为。

对覆写补丁，只复制确实需要的字段。若活动的 LotV/HotS/WoL 依赖已提供基础单位、Actor、模型、声音、死亡设置或武器，就优先用那个基底，避免重复合作补丁。

## 削减规则

- 剥离指挥官成长：`CommanderPrestige*`、精通、指挥官等级、合作成就、顶栏资源、突变钩子、友方指挥官协同，以及指挥官播报/任务响应音效。
- 把合作需求替换为项目需求。典型替换应检查战役科技，或带项目前缀的项目升级。
- 只在移除会破坏目标合法性、自动施放合理性、行为清理或 Actor 创建时，才保留游戏性校验器。删掉那些只用于识别合作指挥官/玩家的校验器。
- 只保留最终 Actor 集合引用到的声音。跳过过场、`ACVO_*`、指挥官响应、教程与界面音效，除非该单位确实需要。
- 只保留最终 Actor 集合引用到的模型。很多目录里混着无关的突变体、威望、放置预览、顶栏或任务专属模型。
- 用项目的数据 ID 前缀重命名最终的自定义数据 ID（对照 `AGENTS.md` 核实；代码示例中用通用的 `My` 前缀）。在实现笔记中记录原始来源 ID。
- 重命名后，手工更新 Actor 字符串项。`UnitBirth.X`、`WeaponStart.X`、`Effect.X.Start`、`Abil.X.Start`、`MorphTo X`、`MorphFrom X`、`ValidateUnit X`、`ValidatePlayer X` 都是精确的字符串链接。

## 各目录的专门说明

`CUnit` 的指令卡里常含合作成长用的被动锁定按钮。除非有需求与技能支撑，它们只是视觉元素。删掉那些宣传指挥官等级或精通的被动锁定按钮。

`CActorUnit` 往往是需要复制的最大一块。它可能引用继承的父级事件、死亡自定义、占地 Actor、线框、图标路径、语音集、放置模型、头像模型，以及大量精确的单位/武器/效果项。这条链不完整时，单位可以机制上可用但看起来是错的。

`CActorAction` 是游戏性效果通往攻击/技能视觉表现的桥梁。直接攻击时，`effectAttack` 通常指向伤害效果。弹体攻击时，动作 Actor 可能使用 `effectLaunch` 与 `effectImpact`。不要因为名字相似就复制无关的动作 Actor，除非选定单位的效果确实引用它们。

`CModel` 条目有时从父级继承全部有用美术，只覆写缩放/半径。没有 `<Model value="..."/>` 的模型，只要父级提供了 `.m3`，仍然有效；请到活动或非活动模型目录中核实父级。

`CSound` 条目可能使用直接的 `AssetArray File` 路径、`TemplateParam` 占位符，或仅靠父级继承。直接战斗/效果音效通常可以连同其 Actor 一起复制。语音与指挥官响应音效往往依赖更广泛的本地化/音频基础设施，除非已被保留下来的单位 Actor 引用，否则普通单位提取应当跳过。

## 代表性示例

完整的非活动单位常常把有用的单位形态、变形技能、Actor 模型替换、死亡模型与武器音效，同依赖专属的成长、顶栏与任务系统混在一起。只保留选定设计所需的记录，然后重写或删除依赖专属系统。

一个复用活动战役攻击视觉表现、只额外加一个模型、头像、图标、属性改动与一个小机制的轻量单位变体，通常比整包依赖拷贝更好维护。

当活动战役导出已定义了接近的基础单位时，就从那里出发，只加上你想要的行为。除非设计明确需要，不要引入指挥官校验或复活钩子。

## 提取前检查清单

在为一个选定单位编辑项目数据之前，先写一份简短的实现笔记，包含：

- 来源单位 ID 与目标项目前缀 ID（代码示例中用 `My...`；实际项目前缀对照 `AGENTS.md` 核实）。
- 非活动来源是完整单位还是覆写补丁。
- 将复用而非拷贝的活动依赖 ID。
- 必需的游戏性记录：单位、技能、武器、效果、行为、校验器、需求、Mover、炮塔、升级。
- 必需的呈现记录：单位 Actor、动作 Actor、模型/声音 Actor、模型、声音、按钮、图标/线框、本地化。
- 刻意排除的合作系统。
- 任何需要精确重命名的 Actor 事件项。

## 交接前提取检查清单

在交出一轮提取的单位/种族工作之前：

1. 把每个被改动的目录当作 XML 解析一遍。
2. 按目录列出所有新增的顶层 `id`；确认每个都有 `ObjectStrings.txt` 的 `Name`（必要时补 `EditorPrefix`/`EditorSuffix`）。
3. 在被改动的 XML 中搜索非活动来源的 ID 引用。每个都必须存在于活动依赖导出中，或被有意复制进项目。
4. 确认指令卡的 `Face` ID 存在于活动依赖或本地 `ButtonData.xml`。优先用活动战役的 `Attack`，而不是合作专属图标。
5. 确认面向玩家的单位在 `GameStrings.txt` 中有 `Unit/Name` 与 `Unit/Tooltip`，且提示由 `CUnit.Description` 锚定。
6. 确认生产按钮在 `GameStrings.txt` 中有 `Button/Name` 与 `Button/Tooltip`，除非它们继承自活动战役按钮。
7. 确认 Actor 链包含必需的 `CModel`、`CSound`、`CTurret`、辅助 `CWeapon` 与 `CValidator` 行。
8. 当活动依赖集缺少所引用的界面文件描述时，剥离合作状态栏钩子（`CustomUnitStatusFrame`、`StatusBarOn`、`SuppressDefaultStatusBar`）。
9. 在认定某条编辑器警告是外部冲突之前，先对所有 `GameData/` XML 文件跑一次 `(catalog type, id)` 重复扫描。

缺失的呈现行表现为空白图标/文字、特效/音频缺失、`GenericUnitFallback` 或编辑器警告——而不是 XML 解析错误。
